# 08: Walking skeleton 1: a listed service shows on the marketplace (receipt)

## What changed
### Contracts
- `contracts/contracts/ServiceRegistry.sol`: `listService` (payable), `topUp` (payable), `getService`, plus `minListingFee` and `serviceCount` getters. Events `ServiceListed` and `BountyToppedUp` as in spec/03. Errors `FeeTooLow(sent, minimum)` and `UnknownService(id)`.
  - The listing fee becomes the service's `bounty`. Anyone can top it up.
  - There is no withdraw function, no `receive` and no `fallback`. The only state-changing functions are the two payable ones.
  - Service ids start at 1, because `RoundManager.openRound` rejects 0.
- `contracts/deploy/local.ts`: `deployLocal` now deploys `ServiceRegistry`. The minimum fee comes from `DEFAULT_ROUND_CONFIG.MIN_LISTING_FEE`, in tinybars.
- `contracts/test/ServiceRegistry.test.ts` (`describe("ServiceRegistry")`) checks:
  - the fee is locked as the bounty
  - a fee below the minimum reverts
  - a top-up adds to the bounty
  - a top-up for an unknown service reverts
  - the seller has no withdraw path (ABI check, a `withdraw()` selector reverts, a plain transfer reverts, the balance is unchanged)
  - both events decode to 06's `EventSchemas` and have the same keys as `eventFixtures`
  - the shared ABI matches the compiled artifact

### Shared
- `packages/shared/abi/ServiceRegistry.ts` (new export `@skeptique/shared/abi/*`) contains:
  - the viem ABI
  - `serviceListedEvent` and `bountyToppedUpEvent`, which turn decoded log args into the shared event shape and validate it with `EventSchemas`

### API
- `apps/api/src/listings.ts`: `createRegistrySource({ client, address })` reads `ServiceListed` logs and each service's bounty from the chain.
  - It fetches the public suite from `<endpoint>/../suite.json` and checks it against `specHash`.
  - It builds a probation `ServiceView`: name and category come from the verified suite; median is null and nRounds is 0. It adds the extra fields `specHash` and `bounty`.
- New routes:
  - `GET /services/:id`, added in `marketplace.ts`, so it works with any source; 404 when the id is unknown.
  - `GET /services/:id/suite` returns the suite when it hashes to `specHash`. Otherwise it returns 502 `{ error, specHash, actualHash }`, or 404 for an unknown service.
- `AppDeps.listings`: when no `marketplace` source is injected, `/services` is served from the registry.
- `apps/api/src/listings.test.ts` covers probation listing, detail, 404s, the suite served, and a hash mismatch rejected.

### Harness
- `startStack` passes a registry source to the API whenever `deployLocal` returns a `ServiceRegistry`.

### Web

### Seed

  - It pays the contract's `minListingFee` and sets ensNode to zero (ticket 12 adds ENS).
  - Price is 1 tinybar per call, defined as a seed fixture.
  - No product path names unit-convert. Only the e2e test and the seed caller pass the name.
- Added `viem` to `@skeptique/scripts`.

## Spec deviations / notes
- **Done-when command syntax.** With pnpm 9.15, `pnpm --filter contracts test --grep ...` fails with `Unknown option: 'grep'`: pnpm parses the flag itself. Use `pnpm --filter contracts test -- --grep "ServiceRegistry"` or `pnpm --filter contracts run test --grep "ServiceRegistry"`.
- **Extra fields beyond ServiceView.** Registry-backed `/services` items also carry `specHash` and `bounty` (tinybars string). The marketplace needs the bounty. `ServiceViewSchema` is not strict, so these items still validate.
- **Services with a bad suite are left out.** A listing whose suite is unreachable or doesn't hash to `specHash` is not in `/services`, because its name and category come from the verified suite. Its `/services/:id/suite` returns 502 with the reason.
- **Units.** Contract amounts are tinybars (spec/notes/hedera-x402.md). The local chain uses the same numbers: the minimum fee is 20e8.
  - The seed sends `minListingFee()` as the tx value. That is correct locally.
  - On Hedera the JSON-RPC value must be in weibars (×10^10). Ticket 21 must scale it when the seed runs against testnet.
- **Scope left to later tickets.**
  - Listing does not open round 1 yet (spec/02 §3 step 1). That needs RoundManager wiring, ticket 14.
  - The bounty is not yet paid out to rounds.
  - `ensName` is `""` until ticket 12.
  - `apps/api/src/index.ts` still passes `contracts: {}`. Wiring production contract addresses is left to ticket 21. The harness wires it locally.
- **Changed ticket 07's harness test.** `starts from a fresh chain on a second boot` asserted block `0x0`, which assumed an empty deploy. It now boots twice and expects the same block height and contract addresses.
- **Pre-existing, unrelated issues.**
  - `scripts/demo/seed.test.ts > allows concurrent deterministic seeds` fails on Windows (EPERM on concurrent `rename`). This ticket doesn't touch it.
  - `biome check .` reports existing errors in `apps/critic`.
  - Playwright could not run here at first: no Chromium installed, and `pnpm` is not on PATH (only `corepack pnpm`). Instead, `next dev` served `/` with status 200, the Marketplace heading and the loading state.
  - Follow-up: after installing Chromium and putting a `pnpm` shim on PATH, `apps/web` `playwright test` passed 12/12 (Marketplace, Critics, Sell, Buyer and Audit pages at 375px and 1280px, nav links, theme toggle).
