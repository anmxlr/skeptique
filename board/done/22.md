# 22: Honest critics are paid and claim

## What changed
- `RoundManager.finalize` (valid round, `nReveals >= kMin`):
  - stores each critic's `claimedCost` from `reveal` (the 5th argument was ignored before);
  - slashes outliers `SLASH_BPS` (as before) and now also slashes **non-revealers** `NOREVEAL_SLASH_BPS` in valid rounds (ticket 25 left this to 22);
  - pays honest critics: each gets `min(claimedCost, COST_CAP)` while the round budget lasts, then all honest critics share the rest of the budget plus the round's slashed stake, pro rata by stake at commit;
  - accrues rewards in `pendingRewards[critic]` and emits `RewardAccrued(roundId, critic, amount)` (spec/03 event);
  - pulls exactly the accrued total into RoundManager: first from the round's slashed stake (`CriticRegistry.releaseSlashed`), the rest from the service bounty (`ServiceRegistry.releaseBounty`). Rounding dust stays in the pools.
- `RoundManager.claim()`: pull payout; zeroes the balance before sending; reverts `NothingToClaim` when nothing is pending (so claiming twice pays once). `receive()` accepts HBAR only from the two registries (`UnexpectedPayment` otherwise).
- `ServiceRegistry.releaseBounty` and `CriticRegistry.releaseSlashed`: callable only by the round manager (`NotRoundManager`), send to the caller. The seller still has no way to withdraw.
- Void rounds are unchanged (no rewards, slashed stake stays in `slashedFunds`, bounty rolls over). The void path now uses the shared `_slash` helper.
- Shared ABIs (`packages/shared/abi/*.ts`) gain `claim`, `pendingRewards`, `COST_CAP`, `RewardAccrued`, `releaseBounty` and errors. `packages/shared/abi/generated/*.json` regenerated with `pnpm --filter contracts export:abis`.
- API `GET /critics` and `GET /critics/:address` (when the round manager is configured) add `honestRounds` (count of `RewardAccrued`), `slashes` (count of `CriticSlashed`) and `pendingRewards` (tinybars string).
- Web critic dashboard (`/critics`) shows stake, honest rounds, slashes and pending rewards, plus a **Claim** button when rewards are pending. The button calls `RoundManager.claim` from the connected wallet (it must be the critic's own account) and reloads the list.
- Tests: `contracts/test/Rewards.test.ts` (reward split, RewardAccrued, claim twice, receive guard, fast-check §7 invariants), `apps/api/src/critics.test.ts` (new fields), `apps/web/test/critics.test.tsx`, `e2e/honest-critics-paid.e2e.test.ts`. Existing tests updated where the behaviour changed on purpose: slashed stake now leaves CriticRegistry, a drained service needs a top-up before reopening, and ServiceRegistry has one more round-manager-only write.

## Spec deviations and interpretations
- **Round budget = one listing fee.** spec/02 says the honest critics share "the remaining bounty", that leftover bounty stays for re-review rounds, and that `MIN_LISTING_FEE` funds the first round. A round therefore spends at most `min(bounty, ServiceRegistry.minListingFee)`, and the rest stays in the pool. With a minimum-fee listing, round 1 spends the whole bounty: the keeper skips services with zero bounty, so **a service is only re-reviewed after the seller tops up**. This changes the demo: before this ticket the bounty was never spent.
- **`COST_CAP` is a contract constant** (1 HBAR = 1e8 tinybars), like ticket 25's `NOREVEAL_SLASH_BPS`, so the constructor and both deploy scripts stay unchanged. spec/02 §2 does not list `cost_cap`.
- Reimbursements come out of the round budget in reveal order. If claimed costs exceed the budget, later honest critics get less reimbursement. With the defaults (7 × 1 HBAR cap vs a 20 HBAR budget) this cannot happen.
- Rounding dust (< number of honest critics, in tinybars) stays in the bounty or in `slashedFunds`, so conservation is exact.
- `MockCriticRegistry.releaseSlashed` only records the amount, because the mock never held stake. Tests that check money flows use the real registries.
- Done-when syntax: `pnpm --filter contracts test --grep ...` is rejected by pnpm 9 (`Unknown option: 'grep'`). I ran `pnpm --filter contracts run test --grep "reward|claim|invariant"`.
- The e2e test was written after the contract and API work (its contract and API halves were already red-then-green in unit tests). The contract and API/web unit tests were written first and seen failing.
