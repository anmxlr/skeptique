# 26: Spend controls and one over-threshold approval

## What changed
- `packages/shared/src/spend.ts`: zod schemas `SpendLimits` (budget, perMerchantCap, allowlist, approvalThreshold, tinybars) and `Approval`.
- `apps/buyer/src/spend.ts`: `createSpendControls({limits, approve, audit, payer})`. `wrap(make)` builds the payer per call with an `onBeforePay` that denies when no limits are set, the merchant is not allowlisted (empty list denies all), the total budget or per-merchant cap would be exceeded; only then, for a price above the threshold, it asks a human. Spend is reserved on allow (so concurrent calls cannot overshoot) and released if the payment throws. After a settled payment (`paid` with a tx id) it posts exactly one `agent_spend {payer, merchant, amount, txId, ts}` through the injected `audit` (the relayer's `createAuditLog` in the CLI). An audit failure is logged, never thrown.
- `apps/buyer/src/approvals.ts`: `createApprovalClient` queues on the API and polls; an error or no answer within `timeoutMs` (default 120 s) is a denial and the request is withdrawn. `fetchSpendLimits`.
- `apps/api/src/buyer-spend.ts`: `GET/PUT /buyer/limits`, `POST/GET /buyer/approvals`, `GET /buyer/approvals/:id`, `POST /buyer/approvals/:id/approve|deny` (409 once answered), CORS for the web app.
- `apps/web/components/spend-controls.tsx` on the Buyer page: limits form and pending queue with Approve/Deny. The Audit page already shows `agent_spend` (ticket 23).
- `apps/buyer/src/cli.ts`: uses the controls when the API has limits set; audit posting needs `HCS_TOPIC_ID`, `RELAYER_ACCOUNT_ID`, `RELAYER_PRIVATE_KEY`, `HEDERA_MIRROR_NODE_URL` (else it logs and skips). Buyer now depends on `@skeptique/relayer`.

## Deviations / notes
- Merchant identity: local mode passes the service origin, Hedera mode passes the x402 `payTo` account, so the allowlist must hold whichever applies. Not checked against a live Hedera payment, and `agent_spend` posting was only tested with a mocked audit client. In local mode nothing settles (`paid` false), so no `agent_spend` is emitted there; spend still counts toward the limits.
- Limits, spent totals and the approval queue are in-memory (API and buyer process restarts reset them). Approval routes are unauthenticated like other demo routes.
- The topic's submit key is the relayer's, so the buyer CLI posts with the `RELAYER_*` key.
- The e2e `beforeAll` timeout is 180 s: the stack boot took about 70 s on this machine.
- Run `pnpm install` in a fresh worktree; this one had no `node_modules`.
