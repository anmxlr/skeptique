# 24: Buyer agent picks by score and pays with no human approving (receipt)

## What changed
### Buyer agent: `apps/buyer`
- `pickService(services, category, strategy)`:
  - `skeptic` picks the highest `rank` among rated services in the category. Unrated (probation) services are skipped.
  - `popularity` picks the most `popularityCalls` and ignores scores.
  - Ties go to the lowest id. If no candidate exists, it throws `NoCandidateError`.
- `explainPick(...)` writes the plain-language reason from the listing's numbers only: rank, median, rounds, confidence, runner-up and skipped unrated services. Popularity picks say they don't consider quality. No LLM is involved, so nothing can change the pick after the fact.
- `runBuyer({ apiUrl, category, task, strategy, payAndCall, signer })`:
  1. `GET /services`, validated with `ServiceViewSchema`
  2. pick and explain
  3. one `payAndCall` at the listed `pricePerCall`

  It has no approval hook and no prompt; spend controls and approval are ticket 26. It returns a `BuyerRun`.
- `publishBuyerRun` posts the run to the API.
- `src/cli.ts` (`pnpm --filter buyer start --api <url> --category <c> --task '<json>'`) runs both buyers on the same task and posts both runs. For now it uses x402 local mode; ticket 15 adds Hedera mode.

### API: `apps/api`
- `POST /calls { serviceId, payer }`: a service reports a settled paid call, and the API answers 202 `{ counted }`.
  - The payer is checked against the injected `isCritic` lookup.
  - Critic payers are never counted, so the seller never has to send or see a critic tag.
- `GET /services` now serves `popularityCalls` from that counter. The marketplace routes are wired into `buildApp` through the new optional `AppDeps.marketplace = { source, isCritic }`.
- `POST /buyer/runs` (validated against the schema) and `GET /buyer/runs` keep the latest run per strategy. The GET sends `Access-Control-Allow-Origin: *` so the web app can read it from its own origin.

### Shared types
- `BuyerRunSchema` / `BuyerRun`: strategy, category, task, pick (a `ServiceView`), explanation, response, txId, paid, at.

### Harness
- `startStack({ api })` passes extra API deps (the marketplace source and critic lookup) into the API it boots.

### Web
- The Buyer page shows a "Skeptic buyer" card and a "Popularity buyer" card side by side, stacking on mobile.
- Each card shows the pick, rank, median, paid calls, the explanation and the result. Under Payment it shows the tx id, or "No on-chain payment (local mode)".
- It polls `/buyer/runs` every 5 s.

## Deviations / notes for the team
- **No HashScan link yet.** `spec/notes/hedera-x402.md` (spike 02) doesn't exist, and AGENTS.md forbids guessing the sponsor's URL format. The page shows the raw tx id; the link lands with 02/15.
- **Who reports paid calls.** Services don't call `POST /calls` yet. A local-mode call has no payer identity, so the report belongs right after x402 settlement, which ticket 15 adds; the e2e test posts the reports itself. Critics are identified by payer address through `isCritic`; the API's production entry point will get that from CriticRegistry once it's wired.
- **Marketplace data.** `apps/api/src/index.ts` doesn't pass a marketplace source yet (no chain-backed source exists). The e2e test uses Dev 2's review-flow medians (100 / 40) as a local fixture.
- **spec/03 additions** (additive only): `POST /calls`, `POST|GET /buyer/runs`, `BuyerRun` in shared. Worth a spec/CHANGELOG line.
- `POST /calls` is unauthenticated, so anyone can inflate popularity. That's the weakness the demo shows, and skeptic ranking doesn't depend on it.
