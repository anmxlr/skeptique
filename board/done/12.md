# 12: Listing creates a role-limited ENS subname (receipt)

## What changed
- `packages/shared/src/ens.ts`: `serviceSlug`, `serviceEnsName`, `ensKeyPrefix`, `scoreKeys`, `SELLER_KEYS` (additive export).
- `apps/relayer`:
  - `grants.ts`: per-key plan. The relayer alone gets the four `eth.<parent>.*` score keys, the seller alone `url`/`description`; nobody gets a resolver-wide role.
  - `relayer.ts`: `createListingRelayer`. It keeps no state; the chain says which subnames exist, so reruns and restarts create no second subname. One failing listing does not stop the rest and is retried next pass.
  - `feed.ts`: reads `ServiceListed` and names each listing from its public suite.
  - `ens/sepolia.ts`: ported from `spikes/ens-sepolia/ens.mjs`. Idempotent `setupNamespace()` (parent, `svc`, `critic` registries), `createSubname` (own resolver, grants, subname registered to the seller with roleBitmap 0), `writeText` (relayer).
  - CLIs: `pnpm --filter @skeptique/relayer ens:setup` (one-time, re-runnable) and `start`.
- `apps/api`: `createRegistrySource({ ensParent })` fills `ensName`.
- `apps/web`: `EnsName` reads the resolver and `url`/`description` through viem (`getEnsResolver`/`getEnsText`) and says "resolved on ENS" only after the resolver answers. Shown on marketplace cards and a new `/services/[id]` page.

## Acceptance
- Seller write to a `skeptique.*` key reverts, seller `url` write succeeds, relayer score write succeeds: mocked in `relayer.test.ts` (in-memory per-key resolver built from the real grant plan) and asserted by simulation in the live test.
- Rerun creates no second subname: `relayer.test.ts` (rerun and restart) and the live test (second pass creates nothing).
- UI reads through the resolver: `web/test/ens-name.test.tsx`.
